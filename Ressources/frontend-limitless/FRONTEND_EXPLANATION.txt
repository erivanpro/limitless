LIMITLESS FRONTEND APPLICATION EXPLANATION
==========================================

This file explains the frontend side of the Limitless application.

There are two frontend projects in this workspace:

1. Limitless-mobile-app-master
   This is the customer and host mobile app built with React Native.

2. Limitless-admin-panel-master
   This is the admin web dashboard built with React, Vite, Material UI, Tailwind, and React Query.

Both frontends talk to the same backend API:

https://limitless-backend-production-578b.up.railway.app/

The backend provides authentication, user profiles, host verification, cars, bookings, payments, chat, notifications, admin review tools, and other shared business logic. The frontends are responsible for collecting user input, showing the correct screens, storing local state, calling the backend endpoints, and reacting to backend responses.

2. MOBILE APP STARTUP FLOW
============================================================

The mobile app starts in:

App.tsx

At startup, the app does several important things:

1. It initializes translations with i18n.
2. It applies the global app status bar style.
3. It checks internet connectivity.
4. It renders the main navigation stack.
5. It mounts the notification listener.
6. It mounts toast UI for app messages.
7. It saves the user's Firebase Cloud Messaging token after the user is known.

The top-level render flow is:

App.tsx
-> I18nextProvider
-> StatusBar
-> NoInternetModal
-> AuthStack
-> NotificationListener
-> Toast

The app stores user data in Zustand and persists it with MMKV. When App.tsx sees a valid user id, it gets the FCM token and sends it to the backend through the notification service.

11. MOBILE BOOKING AND PAYMENT FLOW
============================================================

The booking and payment screen is:

src/screens/PaymentScreen

It uses StripeProvider and the Stripe React Native SDK.

The flow has four steps:

1. SelectDate
2. Payment
3. ConfirmPayment
4. PaymentSummary

SelectDate:

- Loads existing bookings for the car.
- Checks for local time clashes.
- Sends the chosen booking period to the backend for validation.

Endpoints:

GET /car/:id/bookings
POST /booking

The POST /booking call validates the booking and returns price information. This response is stored in booking.store.

Payment:

- Loads saved Stripe payment methods.
- Lets the user select a saved card.
- Lets the user add a new card using Stripe PaymentSheet.
- Lets the user remove a saved card.

Endpoints:

POST /stripe/setup-intent
GET /stripe/payment-methods
DELETE /stripe/payment-method/:id

ConfirmPayment:

- Creates the real payment intent.
- Sends booking and payment metadata to the backend.

Endpoint:

POST /stripe/payment-intent

PaymentSummary:

- Shows the success result.
- Lets the user return to the main app.

The backend is responsible for the actual payment confirmation, booking creation, platform fees, host payout logic, and notification creation.

19. MOBILE FRONTEND TO BACKEND FLOW SUMMARY
============================================================

Normal customer flow:

1. User opens the app.
2. Onboarding appears if they have not seen it before.
3. User signs up or logs in.
4. User completes profile and driving details.
5. App stores token and user profile in local state.
6. App saves the FCM token to the backend.
7. User searches for cars.
8. App calls /car/filter or /car/map.
9. User opens car details.
10. App calls /car/:id.
11. User selects booking dates.
12. App validates booking with /booking.
13. User selects or adds a payment card.
14. App uses Stripe endpoints to setup or retrieve payment methods.
15. User confirms payment.
16. App calls /stripe/payment-intent.
17. Backend creates the booking and sends notifications.
18. User sees the booking in MyOrders.
19. User can chat, cancel, or review depending on booking status.

Host flow:

1. Host signs up or logs in.
2. Host completes personal details.
3. Host completes driving details.
4. Host completes Stripe onboarding if required.
5. Backend and admin verification determine whether the host can fully operate.
6. Host opens Hosting.
7. App calls /car/host to list host cars.
8. Host publishes a car through the publish car wizard.
9. App uploads images.
10. App sends car data to /car.
11. Host can edit the car with /car/:id.
12. Host can publish or unpublish the car.
13. Host receives bookings from customers.
14. Host views them under Orders for My Car.
15. Host can chat with customers.

Chat flow:

1. User taps chat from car details or booking details.
2. App stores sender, receiver, chat type, and chat id if known.
3. App opens SingleChat.
4. App connects to the backend chat socket namespace.
5. App joins or creates the room.
6. Messages are sent and received in real time.
7. Existing messages are also loaded from the REST API.

Notification flow:

1. App requests notification permission.
2. App gets an FCM token.
3. App sends the token to /user/fcm-token.
4. Backend stores the token.
5. Backend sends notifications after important events.
6. App displays foreground notifications through Notifee.
7. User can also view notification history in the Notification screen.

20. MOBILE IMPLEMENTATION NOTES
============================================================

These are important implementation notes found while reading the app:

1. The Axios response interceptor tries to call /auth/refresh on 401. The backend explanation did not show a refresh endpoint, so this should be checked.

2. chat.store.ts and booking.store.ts both use the persisted storage name "chat". This can cause persisted state collisions.

3. getUserCarByIdService appears to call GET /car with an id parameter instead of GET /car/:id. Other detail services correctly use /car/:id.

4. The Hosting screen uses host_onboarding_status to decide whether to show the signed-in host view. Backend-side admin approval still matters for full host behavior.

5. The Stripe publishable key is hardcoded in the mobile app. It should be managed carefully for environment separation.

6. Notification press navigation depends on backend data.navigateTo values matching mobile route names. The values should be checked against the real route names.

30. ADMIN FRONTEND TO BACKEND FLOW SUMMARY
============================================================

Admin login flow:

1. Admin opens the web app.
2. App checks for access_token cookie.
3. If missing, app shows login.
4. Admin submits email and password.
5. App calls /admin/login.
6. Backend returns an access token.
7. App stores token in a cookie and localStorage.
8. App redirects to /users.

Admin user review flow:

1. Admin opens /users.
2. App calls /admin/users with pagination and filters.
3. Admin searches or filters users.
4. App refetches /admin/users.
5. Admin opens a user detail page.
6. App calls /admin/user/:id.
7. Admin reviews profile, ID card, driving license, and host Stripe data.
8. Admin approves or rejects the user.
9. App calls /admin/approve-user/:id or /admin/reject-user.
10. React Query invalidates user queries.
11. List and detail pages update with the new status.


============================================================
31. ADMIN IMPLEMENTATION NOTES
============================================================

These are important implementation notes found while reading the admin panel:

1. Route protection is based on whether the access_token cookie exists. It does not verify the token with the backend on page load.

2. Axios sends the Authorization header from localStorage, while routing checks the cookie. These should stay synchronized.

3. Logout removes the cookie. The localStorage token may remain unless the auth state is overwritten or cleared elsewhere.

4. The admin panel sends a bearer token to /admin/users. This is correct from the frontend side, but the backend should also guard sensitive admin routes.

5. The role dropdown sends lowercase role values such as user and host, which match the backend filter style.

6. The status tabs send Approved, Pending, and Rejected.


============================================================
32. HOW BOTH FRONTENDS WORK TOGETHER WITH THE BACKEND
============================================================

The mobile app and admin panel are separate clients, but they share the same backend and database.

The mobile app creates and updates user data:

- User account
- Profile details
- Driving details
- Host onboarding data
- Car listings
- Bookings
- Payments
- Chats
- Notifications

The admin panel reviews user data:

- Profile details
- ID cards
- Driving license
- Host Stripe account information
- Verification status

The backend is the source of truth.

The mobile app depends on the backend to decide:

- Whether login succeeds.
- Whether a user is verified.
- Whether a host can publish cars.
- Whether a booking is valid.
- Whether payment succeeds.
- Which bookings are active, upcoming, completed, or canceled.
- Which notifications exist.
- Which chat rooms and messages exist.

The admin panel depends on the backend to decide:

- Which users appear in each status tab.
- Which user details are available.
- Whether approve or reject actions succeed.

The shared high-level product flow is:

1. A user signs up in the mobile app.
2. The user uploads identity and driving documents.
3. The backend stores the data.
4. An admin reviews the user in the admin panel.
5. The admin approves or rejects the user.
6. The backend updates the user's verification status.
7. The mobile app reads the updated status and unlocks or blocks actions.
8. If the user is a host, they can publish cars after the required onboarding and verification.
9. Customers can find, book, pay for, and review cars.
10. Hosts can manage cars and bookings.
11. Both sides can chat and receive notifications.

============================================================
34. SHORT SUMMARY
============================================================

The frontend system has two parts.

The mobile app is the main user and host product. It handles onboarding, authentication, car search, hosting, bookings, payments, chat, notifications, settings, localization, and profile management.

The admin panel is the internal review tool. It lets admins log in, filter users, inspect submitted documents and details, then approve or reject accounts.

Both clients depend on the backend API as the source of truth. The mobile app creates activity and user data. The admin panel reviews and changes verification status. The backend coordinates the database, authentication, Stripe, chat, notifications, and business rules that both frontends rely on.
